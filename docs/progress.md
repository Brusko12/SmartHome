# Последовательное выполнение

По последней инструкции пользователя этапы выполняются автоматически после
успешных проверок. Исходное ТЗ сохранено без изменений; требование остановки
между этапами заменено этой инструкцией.

## Этап 3

Реализованы навигация, главная панель с серверной сводкой, страницы комнат и
устройств, создание/редактирование/удаление через формы, перенос при удалении
комнаты, все панели управления шестью типами устройств, поиск и фильтры.
Данные обновляются запросами к backend. Предусмотрены загрузка, ошибки и пустые
списки; нет декоративных кнопок отсутствующих функций.

Проверены TypeScript, production-сборка, backend и Chromium: создание комнаты и
лампы, включение, сохранение после перезагрузки страницы, адаптивность.
Сценарии и остальные разделы добавляются соответствующими следующими этапами.

## Этап 4

Добавлены CRUD правил/сценариев, типизированный конструктор с упорядоченными
действиями, условиями и триггерами, ручной запуск, результаты каждого действия,
быстрые сценарии на главной панели и журнал причин запуска. Изменение устройства
после commit проверяет подходящие правила. Пересечение порога отличается от
обычного обновления датчика. Есть защита по пути запуска (глубина 8), общий
лимит 64 действий и секундный cooldown для повторного события одного правила.
Ошибка останавливает последующие действия; необязательная удалённая цель
пропускается. Полный результат сохраняется в EventLog.

Проверки: 116 backend-тестов, TypeScript, production-сборка, Chromium: создание
сценария через конструктор, запуск и проверка реального состояния лампы.
Временные триггеры начнут исполняться планировщиком этапа 5.

## Этап 5

Добавлены локальный runtime и CRUD расписаний с конструктором в UI. Расписание
запускает сценарий или упорядоченные действия. Следующий запуск вычисляется в
часовом поясе дома; пропущенные при закрытом приложении события не догоняются.
Перед выполнением запуск фиксируется в SQLite, поэтому перезапуск не повторяет
уже заявленное выполнение. При аварийном завершении между фиксацией и командой
действие может остаться невыполненным; автоматического повтора нет.

Симулятор использует мощность и время для кВт·ч, ограниченную скорость изменения
температуры, детерминированные показания датчика и срок сброса движения. Якорь
симуляции сохраняется отдельно от времени изменения состояния. При старте он
сбрасывается к текущему времени: закрытое приложение не симулирует устройства.
Перед командой/изменением мощности учитывается прошедший интервал старого состояния.
Изменения симуляции проходят через SQLite и триггеры правил.

Миграции 0002/0003 добавляют Home.settings и DeviceState.simulated_at без потери данных.
Добавлен только tzdata — база IANA-зон для Windows, без внешнего сервиса.
Фоновый процесс защищён OS file lock и завершается вместе с lifespan.

Проверки: 130 backend-тестов, TypeScript/сборка, Chromium: реальный автоматический
сброс движения и создание расписания с вычисленным следующим запуском.
Отдельно проверены DST, повторный tick без дублирования и освобождение блокировки.

## Этап 6

Добавлены первоначальная настройка через UI, локальные сессии в SQLite с хешами
токенов, HttpOnly/SameSite cookie, CSRF и проверка Origin. Изменение пароля
завершает все сессии. Локальная авторизация одного пользователя не использует
облако, JWT-секреты по умолчанию или стандартные пароли.

Реализованы история с типом/устройством/датой/порядком/пагинацией, просмотр
изменённых значений, сохранение контекста удалённого устройства; настройки дома,
часового пояса, UI и симуляции; диагностика backend, SQLite и фоновых задач.

Резервные копии создаются SQLite backup API, передаются файлами без загрузки
всей базы в память. Импорт до 2 ГБ проверяет целостность, внешние ключи, схему,
структуру данных и парольные хеши до замены. Перед заменой автоматически
сохраняется страховочная копия. Общий барьер запросов и runtime исключает
параллельную запись во время восстановления; сессии после импорта удаляются.

Демонстрационные данные предлагаются после настройки: 11 устройств, три сценария,
правило движения и утреннее расписание. Создание идемпотентно; можно отказаться.

Проверки: 137 backend-тестов, TypeScript/production build. Chromium прошёл
регистрацию с чистой базой, демонстрацию, экспорт, изменение дома, подтверждённый
импорт, повторный вход, фильтр истории, диагностику и выход на мобильной ширине.
Ошибок JavaScript и внешних запросов не было.

## Этап 7: реализация и доступные проверки

FastAPI раздаёт production React и безопасно обрабатывает SPA-маршруты.
Launcher выбирает свободный loopback-порт, дожидается API, открывает браузер,
переиспользует работающий экземпляр и предоставляет штатное завершение из UI.
Ресурсы, миграции и tzdata включены в PyInstaller spec. Windows-скрипт и workflow
создают ZIP только после тестов и проверки настоящего EXE.

142 автоматизированных теста проходят. Контрольный Linux PyInstaller-процесс
прошёл регистрацию, команду, второй запуск, завершение и перезапуск с сохранением.
Обнаруженная зависимость readiness-проверки от системного HTTPS устранена и
покрыта регрессией. Windows EXE затем собран и проверен на Windows runner;
подробности — testing-report.md. Ручная приёмка чистой Windows 10/11 остаётся
невыполненной частью этапа 8.


## Этап 8: Windows-автопроверка

После восстановления GitHub-доступа исходники опубликованы. Общие проверки
прошли на Linux и Windows (по 142 теста), frontend собрался. Workflow создал
Windows EXE и проверил его без Python/Node в PATH дочернего процесса.
Вход, команда, повторный запуск, штатное завершение и сохранение состояния
после перезапуска прошли. ZIP скачан, проверены контрольная сумма и ресурсы.
Ручная приёмка на чистой пользовательской Windows и без интернета ещё требуется.
