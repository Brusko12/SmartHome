# База данных этапа 1

Миграция: `0001_initial_schema`. Все девять сущностей имеют целочисленный
первичный ключ, `created_at` и `updated_at` в UTC. Идентификатор устройства
уникален внутри локальной базы; SQLite AUTOINCREMENT предотвращает повторное
использование удалённых идентификаторов. Дефолты создаются ORM; записи через сырой SQL
должны явно задавать обязательные значения.

| Модель / таблица | Основные поля | Связи |
|---|---|---|
| User / users | username, password_hash | Один пользователь → несколько домов |
| Home / homes | name, timezone, owner_id | Один дом → комнаты, устройства, правила, расписания, интеграции, события |
| Room / rooms | name, icon, home_id | Одна комната → несколько устройств |
| Device / devices | name, device_type, adapter_type, parameters | Дом, обязательная комната, необязательная интеграция |
| DeviceState / device_states | values, source, device_id | Одно текущее состояние на устройство |
| Automation / automations | name, kind, enabled, trigger, conditions, actions, last_run_at | Дом; связанные расписания |
| Schedule / schedules | hour, minute, weekdays, enabled, automation_id, actions, last_run_at, next_run_at | Дом; сценарий/правило либо собственный упорядоченный набор действий |
| EventLog / event_logs | event_type, source, description, status, details, device_id | Дом; необязательное устройство |
| Integration / integrations | name, adapter_type, enabled, config | Дом; связанные устройства |

## Ограничения

- Имена пользователей уникальны. Имена комнат и интеграций уникальны внутри
  дома. Пустые основные имена запрещены.
- Устройство обязательно принадлежит комнате своего дома. Составные внешние
  ключи также запрещают привязку интеграции и расписания к сущности другого дома.
- Поддерживаемые типы устройств: `light`, `thermostat`, `outlet`, `motion_sensor`,
  `climate_sensor`, `tv`. Тип адаптера хранится отдельно, по умолчанию `virtual`.
- `DeviceState` содержит текущее состояние, а не историю. История предназначена
  для `EventLog`. Уникальный `device_id` не допускает два текущих состояния.
- `Automation.kind`: `scenario` для ручного сценария без триггера, `rule` для
  правила с триггером. Это одна таблица, как допускает ТЗ. Массив `actions`
  сохраняет порядок. Исполнение и семантическая валидация действий — этап 4.
- Расписание: часы 0–23, минуты 0–59, непустой набор уникальных дней 0–6
  (понедельник = 0). Выполняется либо связанная автоматизация, либо собственные
  действия. Одновременно указать оба варианта или ни одного нельзя.
- Часовой пояс хранится в Home; расчёт следующих запусков и валидация часового
  пояса появятся с планировщиком. Значение по умолчанию — `UTC`.
- Автоматизации, расписания и интеграции по умолчанию отключены.
- Статус события: `info`, `success`, `error`. Индексы предусмотрены для внешних
  ключей, типа события и пары дом/время события.

## JSON и изменения

JSON-поля валидируются Pydantic при записи через SQLAlchemy: только JSON-значения,
нужная форма объекта/массива, без NaN, infinity и произвольных Python-объектов.
Значения JSON следует заменять целиком (`entity.values = {…}`); вложенные
изменения словаря на месте автоматически не отслеживаются SQLAlchemy.

Форма и диапазоны параметров конкретных типов устройств, условия правил и
команды ещё не реализованы. Их валидация будет обязательной в сервисах
соответствующих этапов. На этапе 1 API изменения JSON не предоставляет.

## Политика удаления

- Удаление пользователя с домами, дома с зависимыми сущностями, комнаты с
  устройствами, используемой интеграции и автоматизации с расписаниями
  блокируется (`RESTRICT`). Это действует в БД и через ORM, включая загруженные
  коллекции. Перенос/подтверждение в UI появится с CRUD.
- Удаление устройства удаляет только его текущее состояние (`CASCADE`).
- События сохраняются, их `device_id` становится `NULL` (`SET NULL`). Для
  сохранения контекста сервисы должны записывать имя/тип устройства в `details`.
- Ссылки внутри JSON не являются внешними ключами. Проверка существования
  целей команд и корректное поведение при их удалении — задача будущих сервисов.

## Начальные данные и перенос

Инициализация сейчас создаёт только схему. Автоматических пользователей,
паролей и демонстрационного дома нет. По ТЗ демоданные должны предлагаться
после настройки локального пользователя, а не создаваться при каждом запуске.

База находится вне репозитория и будущей временной распаковки PyInstaller.
Экспорт/импорт через SQLite backup API — этап 6. Перенос одной папки приложения
не переносит данные из профиля пользователя. Готового механизма переноса
данных на этапе 1 нет.
