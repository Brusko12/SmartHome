**GitHub-репозиторий:** https://github.com/Brusko12/SmartHome.git

---

## 1. Цель проекта

Разработать полноценное локальное приложение SmartHome для управления виртуальными устройствами умного дома.

Приложение должно позволять пользователю управлять устройствами, создавать комнаты, настраивать автоматизации, запускать сценарии, просматривать историю событий и отслеживать состояние системы.

Главная задача — создать не статический макет, а работающую программную систему с интерфейсом, серверной логикой, базой данных и симуляцией устройств.

### Ключевые требования

- Приложение запускается двойным нажатием на ярлык рабочего стола.
- Для запуска готовой сборки не нужны IDE, Python, Node.js или терминал.
- Приложение работает без подключения к интернету.
- Все изменения сохраняются в SQLite.
- После закрытия и повторного запуска данные остаются на месте.
- Виртуальные устройства обладают настоящей программной логикой.
- Автоматизации реально изменяют состояния устройств.
- Интерфейс современный, удобный и визуально целостный.
- Приложение можно перенести на другой компьютер Windows.
- Архитектура допускает подключение физических устройств в будущем.

## 3. Архитектура системы

Система должна иметь следующие независимые логические слои:

1. **Frontend:** интерфейс пользователя.
2. **API:** HTTP-интерфейс взаимодействия.
3. **Services:** бизнес-логика устройств, сценариев и автоматизаций.
4. **Device adapters:** унифицированное взаимодействие с устройствами.
5. **Persistence:** хранение и получение данных из SQLite.
6. **Launcher:** запуск приложения на Windows.

Frontend не должен напрямую обращаться к SQLite.

Бизнес-логика не должна находиться внутри компонентов React.

Все операции с состояниями устройств должны проходить через backend.

## 7. Виртуальные устройства

В первой версии физические устройства не подключаются.

Все устройства должны работать через программный симулятор.

Каждый экземпляр устройства имеет уникальный идентификатор, тип, имя, комнату, состояние, параметры и время последнего изменения.

### 7.1. Умная лампа

Функциональность:

- Включение и выключение.
- Настройка яркости от 0 до 100%.
- Выбор цвета.
- Отображение текущего состояния.
- Сохранение параметров.

Изменение яркости или цвета должно влиять на состояние конкретного устройства.

### 7.2. Термостат

Функциональность:

- Текущая температура.
- Целевая температура.
- Режимы: Off, Heating, Cooling, Auto, Eco.
- Изменение целевой температуры.
- Симуляция постепенного изменения текущей температуры.

Температура должна изменяться по понятной детерминированной модели с учётом целевого значения, режима и прошедшего времени.

### 7.3. Умная розетка

Функциональность:

- Включение и выключение.
- Отображение текущей мощности.
- Накопленное энергопотребление в кВт·ч.
- Симуляция энергопотребления только при включённом состоянии.

Энергопотребление должно рассчитываться из мощности и времени, а не представлять собой произвольное число.

### 7.4. Датчик движения

Функциональность:

- Состояния «Движение обнаружено» и «Нет движения».
- Кнопка ручной симуляции движения.
- Автоматический сброс состояния спустя установленный интервал.
- Запись событий в журнал.
- Возможность использовать события как триггеры автоматизации.

### 7.5. Датчик температуры и влажности

Функциональность:

- Показания температуры.
- Показания влажности.
- Симуляция изменения показаний.
- Отображение времени последнего обновления.
- Использование показаний в автоматизациях.

### 7.6. Телевизор

Функциональность:

- Включение и выключение.
- Управление громкостью от 0 до 100.
- Режим Mute.
- Сохранение состояния.

### Общие требования

Все команды должны проверяться backend.

Нельзя передавать произвольные неподдерживаемые параметры.

После выполнения команды необходимо:

1. Проверить корректность команды.
2. Изменить состояние.
3. Сохранить изменение в SQLite.
4. Зарегистрировать событие в журнале.
5. Вернуть актуальное состояние frontend.

После перезапуска приложения сохраняемые параметры должны восстановиться.

## 8. Абстракция устройств

Создать общий интерфейс адаптеров устройств.

Пример логического контракта:

```python
class DeviceAdapter:
    def connect(self): ...
    def disconnect(self): ...
    def get_state(self): ...
    def execute_command(self, command, params): ...
    def get_connection_status(self): ...
```

Точный интерфейс может быть асинхронным и должен определяться реализацией.

### Первая реализация

`VirtualDeviceAdapter`

Отвечает за управление виртуальными устройствами и моделирование их поведения.

### Возможные будущие реализации

`MQTTDeviceAdapter`

`HomeAssistantAdapter`

В первой версии эти интеграции реализовывать не требуется.

Система должна позволять добавить новые адаптеры без переписывания пользовательского интерфейса и основной бизнес-логики.

## 9. Сценарии

Сценарий — набор команд для нескольких устройств, запускаемый вручную.

### Предустановленные сценарии

**«Я ушёл»**

- Выключить основные лампы.
- Выключить выбранные розетки.
- Переключить термостат в Eco.

**«Доброе утро»**

- Включить освещение спальни.
- Установить комфортную яркость.
- Установить комфортную температуру.

**«Ночной режим»**

- Выключить основное освещение.
- Включить ночное освещение, если оно настроено.
- Переключить термостат в экономичный режим.

### Управление сценариями

- Создание.
- Изменение.
- Удаление.
- Запуск.
- Включение и отключение.
- Настройка последовательности действий.
- Просмотр результата выполнения.

Предустановленные сценарии должны ссылаться на реальные существующие устройства и не должны падать при отсутствии необязательных устройств.

Действия сценария должны выполняться в определённом порядке.

При ошибке необходимо зарегистрировать её и показать пользователю, какие действия были выполнены, а какие нет.

## 10. Автоматизации

Автоматизации должны запускаться при наступлении событий или выполнении условий.

### Принцип работы

**Триггер → условия → действия**

Пример:

```text
Триггер:
Обнаружено движение в гостиной

Условие:
Лампа выключена

Действие:
Включить лампу гостиной
```

### Поддерживаемые триггеры

- Изменение состояния устройства.
- Обнаружение движения.
- Изменение показаний датчика с пересечением порога.
- Наступление заданного времени.

### Поддерживаемые условия

- Устройство включено или выключено.
- Температура выше или ниже значения.
- Влажность выше или ниже значения.
- Значение числового параметра в заданном диапазоне.

### Поддерживаемые действия

- Включить или выключить устройство.
- Изменить яркость.
- Изменить цвет.
- Установить температуру.
- Изменить режим термостата.
- Изменить громкость телевизора.
- Запустить сценарий.

### Управление

- Создание правил.
- Редактирование.
- Включение и выключение.
- Удаление.
- Ручное тестирование.
- Просмотр последнего запуска.

Необходимо исключить неконтролируемые циклы автоматизаций.

Рекомендуется использовать защиту от повторного срабатывания, ограничение глубины вложенных действий и журнал причин запуска.

При перезапуске приложения активные правила должны восстанавливаться из SQLite.

### Основные таблицы

### Требования к моделям

Каждая сущность должна иметь первичный ключ.

Связи должны использовать внешние ключи.

Необходимо корректно настроить каскадное удаление или запрет удаления там, где это необходимо.

Для параметров, зависящих от типа устройства, допустимо использовать JSON-поля с обязательной валидацией через Pydantic.

### Миграции

Использовать Alembic.

Не пересоздавать базу при каждом запуске.

Инициализация начальных данных должна быть идемпотентной.

### Местоположение базы

Для готовой Windows-сборки:

```text
%LOCALAPPDATA%\SmartHome\data\smart_home.db
```

Пользовательские данные нельзя хранить внутри временной папки распаковки PyInstaller.

Для переносимости предусмотреть документированный механизм экспорта и импорта базы, например с использованием SQLite backup API.

## 16. Симуляция и фоновая логика

Виртуальные устройства должны обладать поведением, соответствующим их типу.

### Примеры

Термостат постепенно изменяет температуру.

Розетка накапливает энергопотребление.

Датчик движения генерирует событие при ручном тестировании.

Датчики температуры и влажности способны изменять показания по контролируемой модели.

Симуляция должна использовать понятные диапазоны и ограничения.

Необходимо отделить изменения состояния по команде пользователя от изменений, вызванных самой симуляцией.

Фоновые задачи должны корректно запускаться и останавливаться вместе с приложением.

Должна существовать защита от нескольких одновременно работающих экземпляров симулятора для одной базы данных.

## 19. Windows-запуск

Это одно из наиболее важных требований.

### Пользовательский сценарий

1. Пользователь дважды нажимает на ярлык SmartHome на рабочем столе.
2. Приложение запускает локальный сервер.
3. Проверяет доступность API.
4. Автоматически открывает интерфейс в браузере.
5. Пользователь работает с системой.
6. Все данные сохраняются в SQLite.

Нельзя требовать ручного запуска Python, npm, Uvicorn или терминала.

### Требования к launcher

- Отсутствие видимого окна консоли при обычном запуске.
- Запуск локального сервера только на `127.0.0.1`.
- Автоматический выбор или контролируемое использование доступного порта.
- Проверка готовности сервера перед открытием браузера.
- Предотвращение повторного запуска второго экземпляра.
- Понятные сообщения об ошибках.
- Корректное завершение backend.
- Отсутствие зависших фоновых процессов.

Поскольку интерфейс работает в браузере, предусмотреть явное действие «Завершить SmartHome», которое корректно останавливает локальный сервер.

Закрытие вкладки браузера само по себе не обязано завершать приложение; это поведение необходимо объяснить пользователю.

## 20. Переносимость

### Итоговая структура

```text
SmartHome-Release/
├── SmartHome.exe
├── resources/
├── README.txt

```

Вместо указанной структуры допускается сборка PyInstaller в режиме `onefile`, если все ресурсы корректно включены.

Приложение должно работать после распаковки на другом совместимом Windows-компьютере.

На целевом компьютере не должны требоваться:

- Python.
- Node.js.
- Git.
- VS Code.
- IDE.
- Интернет.
- Установка отдельных библиотек разработчика.

В случае переноса пользовательских данных необходим отдельный экспорт и импорт базы.

Один EXE сам по себе не обязан переносить данные, сохранённые в `%LOCALAPPDATA%`.

Готовую сборку необходимо создавать и тестировать на Windows.

## 21. Безопасность и надёжность

- Локальный API не должен быть доступен из внешней сети.
- Все команды должны проверяться на backend.
- Пользовательский ввод валидируется.
- Пароли хешируются.
- SQL-запросы выполняются через ORM или параметризованные запросы.
- Ошибки не должны приводить к неконтролируемому падению приложения.
- Запрещено хранить секреты в Git.
- Необходима защита от рекурсивных автоматизаций.
- Сохраняемые изменения должны выполняться с корректным управлением транзакциями.
- Резервное копирование SQLite должно выполняться безопасным способом.
- Не должно быть скрытых обязательных обращений к облачным сервисам.
